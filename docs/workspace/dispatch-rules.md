# Muse 1 自动拆解、分配、汇总规则（第二阶段，2026-11-13）

> 适用：Muse 1（总指挥）把用户的一段需求拆成任务、建 Issue、分派、汇总。
> 本文件是 `docs/workspace/agent-protocol.md`（12 类消息、标签状态机、轮询规则）的
> 第二阶段补充：拆分怎么做、怎么查重、怎么按能力分派、最后怎么汇总。
> 唯一任务中心仍是 GitHub Issues，PR 仍是代码交付载体；能力标签见
> `docs/workspace/agent-registry.md`，标签定义见 `.github/labels.yml`。
> 模板见 `.github/ISSUE_TEMPLATE/agent-task.md`；自动检查见
> `.github/workflows/dispatch-check.yml`。

## 一、拆分规则

### 1.1 一段需求怎么拆

1. 先把需求写成一句话的目标（做什么、为什么做），再拆成任务；写不出目标的需求先问用户，不硬拆。
2. 一个任务 = **一个可独立验证的交付**：改完能单独开 PR、单独跑 CI、单独冒烟、单独合并。
   拆得太碎（改两行也一个任务）或太粗（一个任务横跨前后端还带数据库）都不合格。
3. 拆分粒度参考：一个任务的文件修改范围通常集中在**一个子系统内**（如只改
   `apps/my_app/backend/services/` 或只改 `apps/portal/src/components/`），
   跨子系统的需求拆成多个任务，用依赖串起来。
4. 任务之间只允许两种关系：**依赖**（前置任务不完成，后续任务不能认领）或
   **无关**（可以并行）。不存在“半依赖”：要么写进依赖，要么不写。
5. 每个任务必须能说出“做完怎么算通过”——写不出验收标准的任务不建 Issue。

### 1.2 每任务必填字段（与 Issue 模板一一对应）

| 字段 | 要求 |
| --- | --- |
| 任务说明 | 一句话说清做什么、为什么做；不写背景的任务不认领 |
| 负责人 | 三选一：`agent:muse-2` / `agent:muse-3` / `agent:grok`；协调类任务才用 `agent:muse-1`（Muse 1 不写业务代码） |
| 优先级 | P0：阻塞主线 / P1：本轮要做 / P2：可延后 |
| 文件修改范围 | 列出允许改的文件或目录；认领后只能改这个范围，超出范围先在评论里说明并等 Muse 1 确认 |
| 依赖任务 | 前置任务全部完成（`state:merged`）后才能认领；写 `depends on #N`，无依赖写“无” |
| 验收标准 | 可逐条打勾的验收项；验收不通过即返工，不由口头确认代替 |
| 所属分支 | 一任务一分支，命名 `agent/<任务>`（如 `agent/task-12-data-access`） |
| 当前状态 | 状态只用标签表示：`state:todo` → `state:claimed` → `state:in-review` → `state:qa-ready` → `state:qa-passed` / `state:qa-failed` → `state:merged` |

缺必填字段的 Issue 由 `dispatch-check.yml` 发提醒评论补齐（见第五节）。

### 1.3 拆分后自查（建 Issue 前逐条过）

- [ ] 每个任务都有独立的验收标准，且能在不依赖其他未完成任务的情况下验证。
- [ ] 每个任务的文件修改范围都已列出，没有“顺便改一下”的模糊地带。
- [ ] 依赖关系已写进 Issue（`depends on #N`），没有口头约定的依赖。
- [ ] 每个任务都打了 `phase:<n>` 标签和负责人标签（`agent:muse-2/3/grok`）。
- [ ] 涉及生产环境、数据库结构、VMAX、nginx、生产服务重启的任务已打 `risk:high`
      标签，合并前须用户明确批准（见 `agent-protocol.md` 第三节）。

## 二、文件范围查重规则

查重在**拆分时**做一次（Muse 1 人工核对），**认领前**再做一次（Worker 按协议
第五节先拉 GitHub 确认）；两道关都过才能并行。

### 2.1 查重方法

1. 把所有任务的“文件修改范围”并排比对，找出**重叠文件**（同一文件出现在两个
   任务的修改范围里）。
2. 重叠分两级：
   - **高冲突**：同一文件的同一区域（如同一函数、同一配置段）都要改，
     或改动会互相覆盖（如两人各改同一份 `task_registry.py` 的登记表）。
   - **低冲突**：只改同一文件的不同区域，且改动互不影响（如一人改 A 函数、
     一人改 B 函数），但仍需警惕合并时的上下文冲突。

### 2.2 重叠任务串行化

- **有重叠就串行，不并行**：后一任务在 Issue 里写 `depends on #N`（依赖前一任务），
  前一任务 `state:merged` 之前，后一任务不得认领；`dispatch-check.yml` 会给
  依赖未满足的任务打 `state:blocked` 标签。
- **高冲突文件强制串行**：即使只是同一文件的不同区域，只要文件是高频改动点
  （任务登记表、路由表、i18n 字典、共享配置），也按高冲突处理，不并行。
- **零冲突提交**：串行化的任务合并时不产生冲突；若合并仍出现冲突，由开发
  Agent 自己 rebase 解决（见 `agent-protocol.md` 第六节），不自动合冲突 PR。
- **认领前复查**：Worker 认领前必须先拉 GitHub，确认依赖的 Issue 已关闭、
  任务仍是 `state:todo` 且无人认领，避免撞单（见 `agent-protocol.md` 第五节）。

### 2.3 查重失败的后果

- 两个并行任务改了同一文件且合并冲突：后合并的一方负责 rebase 解决；
  若冲突涉及业务逻辑（不是纯文本冲突），Muse 1 介入重排任务。
- 发现漏查重（并行任务事后才发现重叠）：立即把后启动的任务改成依赖前一任务
  （补 `depends on #N` + `state:blocked` 标签），已产生的冲突由后者解决。

## 三、按依赖与能力分派的规则

### 3.1 能力标签（唯一依据：`agent-registry.md`）

| Agent | 能力 | 能接的任务 |
| --- | --- | --- |
| Muse 1 | 需求分析、任务拆分、文件范围查重、进度协调、结果整合、冲突处理、QA 结果裁决 | 只接协调类任务，**不写业务代码** |
| Muse 2 | Python 后端、FastAPI、SQLite/PG、任务系统、数据访问层 | 后端、任务系统、数据层任务 |
| Muse 3 | 前端（React / 门户）、services 重组、文档 | 前端、重组、文档任务 |
| Grok Bot | D:\02 冒烟测试（§8.2–8.4）、离线 pytest、结构化测试报告 | 只接 QA 任务，**第一阶段不写代码** |

能力标签是认领匹配的依据，不是硬限制：任务需要的能力超出负责人已有能力时，
由 Muse 1 改派，不硬上。

### 3.2 分派顺序

1. **先排依赖**：依赖链上的任务按拓扑顺序分派；依赖未满足的任务不分派
   （建 Issue 时就打 `state:blocked`，等 `dispatch-check.yml` 在依赖满足后摘掉）。
2. **再按能力匹配**：每个任务分给能力标签最贴合的 Worker；能力重叠时看当前
   负载（谁手头的 `state:claimed` 任务少、谁的租约快到期）。
3. **最后看并行度**：无依赖、无文件重叠的任务可以并行分派；有重叠的按第二
   节串行化，不并行。
4. **改派规则**：Worker 发 TASK_BLOCKED（能力不够、依赖卡死、等用户决定）
   后，Muse 1 在 24 小时内改派或升级给用户；改派时在原 Issue 发评论说明
   原因，新负责人重新认领（原认领评论作废，租约重新计时）。

### 3.3 认领与租约（沿用协议第五节）

- 认领评论首行：`<!-- agent-claim: muse-2, <ISO 8601 UTC 时间> -->`，
  同时打 `state:claimed` 标签。
- 认领后 **4 小时无进展**（无 push、无评论）即租约过期，Muse 1 摘
  `state:claimed` 标签重派。
- TASK_ASSIGNED **24 小时无人认领**：Muse 1 在 Issue 下追问；**48 小时无回应**：
  升级给用户，由用户决定换人或改派。

## 四、最终汇总格式

需求的全部任务都走到 `state:merged`（或明确标记不再做）后，Muse 1 在**需求的
总 Issue**（或当初拆分时建的跟踪 Issue）下发一条汇总评论，机器可读头 +
人可读正文：

```
<!-- agent-msg: TASK_COMPLETED, task: #N, from: muse-1, at: <ISO 8601 UTC 时间> -->
```

人可读正文逐项列出（每任务一行，不漏）：

| 任务 | 分支 | PR | CI | 冒烟 | 合并提交 |
| --- | --- | --- | --- | --- | --- |
| #17 TASK-02 | `agent/task-17-xxx` | #16 | 10/10 绿 | 通过（HEAD SHA：`abc1234`） | `8ee4b60` |
| #18 TASK-03 | … | … | … | … | … |

汇总评论还必须包含：

- **未完成 / 阻塞项清单**：哪些任务没做、为什么没做（依赖卡死 / 等用户决定 /
  打了 `needs-replan` 标签），以及下一步由谁处理。
- **返工记录**：QA 失败过的任务、修复轮次（第 1/2/3 次）、最终结果。
- **测试结果与 Commit 的对应关系**：每项冒烟结果都写明 HEAD SHA；过期测试
  结果（HEAD 已变）不得计入通过（见 `agent-protocol.md` 第二节补充规则）。

汇总发完后，关闭总 Issue；各子任务 Issue 由各自的 PR_MERGED 流程关闭
（打 `state:merged` 标签后关闭）。

## 五、自动检查（`dispatch-check.yml` 的行为）

工作流只做提醒与标签，**不自动合并、不自动关闭 Issue**：

1. **缺字段提醒**：新开的 agent-task Issue 缺必填字段时，在 Issue 下发提醒评论
   （列出缺了哪几项），同一个 Issue 只提醒一次，不重复刷屏。
2. **依赖阻塞**：Issue 的 `depends on #N` 所指任务未完成（未关闭）时，打
   `state:blocked` 标签，并评论说明被哪个依赖挡住。
3. **依赖解除**：依赖任务全部完成后，自动摘掉 `state:blocked` 标签，并评论
   说明依赖已满足、可以认领。
4. **触发时机**：Issue 新建 / 编辑 / 关闭 / 标签变化时即时检查，外加每小时
   一次定时巡检兜底（覆盖“依赖任务关闭时没触发”的情况）。

> 真正的“分派下一个任务”不在本工作流里：PR 合入 main 后由
> `auto-dispatch.yml` 自动找就绪任务并发 TASK_ASSIGNED 评论
> （见 `docs/workspace/github-automation.md` 第二节）。本工作流只做
> 检查与标签，不替 builder 认领、不发分派评论。
