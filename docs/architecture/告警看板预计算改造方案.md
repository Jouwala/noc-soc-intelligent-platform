# 告警看板预计算改造方案

> 适用：`apps/my_app` 告警看板（`/api/alarm-dashboard/*`，前端 `pages/AlarmDashboard.tsx`）
> 代码基线：commit `49e42d6`｜日期：2026-11-22
> 配套代码：`backend/services/dashboard/snapshot_store.py`、`backend/services/alarm/alarm_snapshot.py`、`backend/routers/alarm_dashboard.py`、`backend/task_registry.py`

---

## 1. 一句话

**数据写完就把看板要的结果算好，存一份快照；用户打开页面时只取现成的 JSON。** 不引入 Redis，快照存在现有数据库的一张小表里，Web 进程再加一层内存缓存。

---

## 2. 现状：为什么慢（基于代码阅读，需要用访问日志确认）

| 接口 | 现在每次请求做什么 | 慢点 |
|---|---|---|
| `GET /overview` | `SELECT * FROM realtime_alarm`，在 Python 里逐行聚合；调用 `_history_metrics_sql()`；调用 2–3 次 `_last_alarm_sync_iso()` | ① 历史指标只缓存 60 秒，过期后要对 7 天的 `history_alarm` 全表聚合，而且列都是 TEXT，要逐行用正则和 CAST 转换（`alarm_dashboard.py:136-189`）；② `_last_alarm_sync_iso()` 查 `task_execution_log ... ORDER BY completed_at DESC`，仓库里**没找到** `(task_id, completed_at)` 索引，这张表 7 天里光 `eflow_active_alarm` 就有约 1 万条记录 |
| `GET /alarm-overview` | `_alarm_category_counts`、`_recovery_mttr`、读 xlsx | ① `_recovery_mttr` **完全没有缓存**，每次请求都对 `history_alarm` 做正则聚合（`:762-800`）；② xlsx 缓存 60 秒，过期后要用 openpyxl 重读整页（`:804-908`） |
| `GET /history-drilldown` | 缓存 60 秒，过期后 `pd.read_sql` 整表读入（代码注释写的约 10 万行），再做向量化计算、排序、截取 | 缓存过期后第一次点开下钻，要等整表加载 |
| `GET /realtime-drilldown` | 读 realtime_alarm（约百行）并在内存里过滤 | 本身不慢，但会受到下面"整表重建"的影响 |

另外有几个放大因素：

- **整表重建。** `realtime_alarm` 每分钟用 `if_exists='replace'` 整表重建（`sync_from_eflow_api.py:626`），这个过程中表会短暂消失，索引也要重建。`gis.py` 和 `portal_qc.py` 的注释都记录过读到"表不存在"的情况。
- **大字典序列化。** FastAPI 返回大 dict 时会先做 `jsonable_encoder` 再序列化，响应越大开销越明显。
- **前端只取一次。** 页面只在进入时取一次数据（`cachedGet` 缓存 30 秒），之后不会自动刷新。用户想看最新数据只能刷新页面，刷新又可能正好赶上缓存过期。

> ⚠️ 以上判断来自代码阅读，没有实测。**第 0 步请先用 nginx access.log 量一下**（见第 8 节的脚本），确认 `/api/alarm-dashboard/*` 各接口的 `urt`（后端耗时）p95。如果 `urt` 很小、页面却很慢，瓶颈在前端，这份方案的收益就有限。

## 3. 目标

| 指标 | 目标 |
|---|---|
| `/overview`、`/alarm-overview` 后端耗时 | p95 < 50ms（直接返回快照 bytes） |
| 历史下钻 | p95 < 300ms（查带索引的物化表） |
| 数据新鲜度 | 采集周期 + 几秒（实时每分钟，历史每 3 小时） |
| Worker 挂掉时 | 页面不白屏：自动回退到现算，并提示"数据延迟" |
| 口径 | 与现在逐字一致（复用同一批计算函数） |

## 4. 方案

### 4.1 架构

```
 eFlow API
    │
    ▼
┌────────────────────────── Worker 进程（backend/worker.py）──────────────────────────┐
│ eflow_active_alarm（每分钟）    eflow_history_alarm（每 3 小时）                       │
│   写 realtime_alarm               写 history_alarm                                    │
│        │                                │                                             │
│        └── 成功后 ──► alarm_snapshot.after_realtime_sync / after_history_sync         │
│                         · 复用 alarm_dashboard 里现有的计算函数                         │
│                         · UPSERT _dashboard_snapshot（version+1）                      │
│                         · 重建 _history_alarm_enriched（带索引，原子切换）               │
└──────────────────────────────────────┬──────────────────────────────────────────────┘
                                       │  PostgreSQL（现有库，不新增服务）
┌──────────────────────────── Web 进程（uvicorn）─────────────────────────────────────┐
│ GET /overview                                                                        │
│   └─ snapshot_store.get("alarm:overview")                                            │
│        · 内存里有，且 2 秒内核对过 version → 直接返回（零 SQL）                          │
│        · version 变了 → 按主键读一次 payload（<1ms）                                    │
│        · 没有或超过 5 分钟 → 单飞现算兜底（就是现在的老逻辑）                             │
│   └─ 返回预序列化 bytes + ETag；If-None-Match 命中时返回 304                            │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                       │
                         浏览器：每 60 秒静默刷新，命中 304 时只传约 200 字节
```

**为什么用数据库表，而不是只用内存或 Redis：**
- 采集任务跑在独立的 Worker 进程里（`worker.py` 文件头已说明"调度与执行解耦"），Web 进程的内存缓存它碰不到。所以需要一个两个进程都能访问的地方，现有的 PG 就够了。
- 每次只是一个主键查询加一段几十到几百 KB 的 TEXT，不到 1 毫秒。
- 进程重启后快照还在，不会出现重启后第一个用户要等很久的情况。
- 项目里已经有同样思路的先例：`worker.py` 用数据库表 `task_queue` 做跨进程队列，注释里专门写了"不依赖 Redis/RabbitMQ"。

### 4.2 快照表

```sql
CREATE TABLE IF NOT EXISTS _dashboard_snapshot (
    key            TEXT PRIMARY KEY,   -- 例如 alarm:overview
    version        BIGINT NOT NULL,    -- 每次发布 +1，作为 ETag 和缓存失效依据
    computed_at    TEXT   NOT NULL,    -- 快照算好的时间（UTC）
    source_sync_at TEXT,               -- 源数据同步完成的时间（UTC）
    compute_ms     BIGINT,             -- 计算耗时，便于监控
    payload        TEXT   NOT NULL     -- 已序列化的 JSON
);
```

`snapshot_store.py` 会自动建这张表。写入用 `INSERT ... ON CONFLICT(key) DO UPDATE SET version = version + 1`，SQLite 3.24+ 和 PG 都支持，多个 Worker 组同时写也是原子的。

**本 PR 使用的 key**（`computed_at` 为毫秒精度，用于内存反序列化缓存的 token）：

| key | 内容 | 发布时机 |
|---|---|---|
| `alarm:overview` | `/overview` 的完整响应 | 实时同步后（每分钟） |
| `alarm:realtime_rows` | 实时告警增强行（下钻用，`realtime_alarm` 原始行） | 实时同步后 |
| `alarm:history_metrics` | 历史派单时效 5 项指标 | 历史同步后（每 3 小时） |
| `alarm:history_enriched` | 物化表重建门禁：`{"ok": true/false, "rows": n}` | 历史同步后（重建成功/失败都发） |
| `alarm:recovery_mttr` | 恢复率与 MTTR（按 site_class） | 历史同步后 |
| `alarm:network_avail` | 网络可用率（xlsx）。**读数为空视为失败：不发布、不推进 mtime，下轮重试** | xlsx 修改时间变化时 |
| `alarm:alarm_overview` | `/alarm-overview` 的完整响应 | 以上任一更新后 |

`/alarm-overview` 的响应头额外带 `X-Snapshot-Recovery-Age` / `X-Snapshot-Network-Age`，
`/overview` 带 `X-Snapshot-History-Age`：顶层 `generated_at` 是实时同步时间，而这三块
来自更早的快照，年龄单独透出（**不放进 payload** —— 现算侧没有这些键，放进去会让
shadow 比对永久 mismatch）。

### 4.3 路由重构（`routers/alarm_dashboard.py`）

完整代码见 `backend/routers/alarm_dashboard.py`，改动如下：

1. **把计算逻辑抽成函数，内容不改。** 把 `alarm_dashboard_overview()` 的函数体原样搬进 `_compute_overview_payload(history_metrics=None)`，唯一的改动是历史指标允许由调用方传入。`/alarm-overview` 也同样处理，抽成 `_compute_alarm_overview_payload()`。
2. **新增 `_serve()`。** 优先返回快照。没有快照或快照已过期时，用单飞锁现算一次，结果**只在 Web 进程内存里缓存 60 秒，不写回快照表**，这样"快照过期"的信号会一直保留到 Worker 恢复。现算失败就继续返回旧快照。ETag 匹配兼容 nginx gzip 改出来的弱 ETag（`W/"..."`），写法与 `routers/tasks.py` 一致。
3. **实时下钻。** 把 `rows = _load_realtime_rows()` 换成 `_load_realtime_rows_snap()`。
4. **历史下钻。** 先查 `_history_alarm_enriched`，查不到再回退到原来的 pandas 实现。

### 4.4 Worker 端预计算（`services/alarm/alarm_snapshot.py`）

| 快照 key | 内容 | 触发 |
|---|---|---|
| `alarm:overview` | `/overview` 的完整响应 | 实时同步后；历史同步后也会顺带重发 |
| `alarm:realtime_rows` | 实时增强行（给实时下钻用） | 实时同步后 |
| `alarm:history_metrics` | 历史派单时效的 5 项指标 | 历史同步后 |
| `alarm:recovery_mttr` | 恢复率和 MTTR | 历史同步后 |
| `alarm:network_avail` | 网络可用率 | xlsx 的修改时间变化时 |
| `alarm:alarm_overview` | `/alarm-overview` 的完整响应 | 以上任意一项更新后 |

**两处必须注意，代码里已经处理：**
- **绕开 60 秒内存缓存。** Worker 里也会 import 路由模块，所以计算前要先 `ad._cache.clear()`，否则可能拿到 60 秒前的旧指标。
- **显式写入本次同步时间。** 快照是在采集任务**结束前**生成的，这时本次运行还没写进 `task_execution_log`，`_last_alarm_sync_iso()` 只能查到上一轮的时间。所以要用本次同步时间覆盖 `generated_at`。

**实时刷新不重扫历史表。** 每分钟的实时刷新直接读取 `alarm:history_metrics` 快照，不会每分钟对 10 万行历史数据做一遍正则聚合。

### 4.5 挂到采集任务上（`backend/task_registry.py`）

```python
def _run_eflow_active_alarm():
    from backend.services.eflow.eflow_api_client import fetch_and_save_active_alarm
    res = fetch_and_save_active_alarm()
    rows = res.get("realtime_alarm", []) if isinstance(res, dict) else []
    if rows:
        from backend.services.alarm import alarm_snapshot
        alarm_snapshot.safe(alarm_snapshot.after_realtime_sync)   # 失败只记日志，不影响采集任务本身
    return {"realtime_alarm_count": len(rows)}


def _run_eflow_history_alarm():
    from backend.services.eflow.eflow_api_client import fetch_and_save_history_alarm
    res = fetch_and_save_history_alarm()
    rows = res.get("history_alarm", []) if isinstance(res, dict) else []
    if rows:
        from backend.services.alarm import alarm_snapshot
        alarm_snapshot.safe(alarm_snapshot.after_history_sync)
    return {"history_alarm_count": len(rows)}
```

额外耗时：实时快照预计不到 1 秒（realtime_alarm 只有约百行）；历史部分每 3 小时一次，预计几秒（主要是 pandas 读一遍历史表）。

### 4.6 历史下钻的物化表 `_history_alarm_enriched`

- 历史同步后由 Worker 重建，**复用 `_load_history_df()`**，派生字段和三个超时标记与现在逐字一致。
- 字段包括：14 个输出列、`servertime_ms`，以及三个超时标记 `m_dispatch_delay`、`m_fetch_delay`、`m_overdue`（取值 0/1）。
- 索引：`(servertime_ms DESC)`，以及每个标记各一个 `(flag, servertime_ms DESC)`。
- 下钻查询：`SELECT ... WHERE m_xxx = 1 ORDER BY servertime_ms DESC NULLS LAST LIMIT ?`，再加一条 `COUNT(*)`。
- **原子切换：** 先写 `__new` 表并建好索引，再在一个事务里 `DROP` 旧表并 `RENAME` 新表。PG 和 SQLite 的 DDL 都支持事务，读者最多等几毫秒，不会读到"表不存在"。
- **排序和 pandas 保持一致：** PG 降序时默认把 NULL 排在最前，而 pandas 的 `sort_values` 把 NaN 排在最后，所以查询必须写 `NULLS LAST`。SQLite 的索引定义不支持这个语法，代码里按方言分开处理。

```tsx
const [stale, setStale] = useState(false)

const load = useCallback((silent = false) => {
  if (!silent) setLoading(true)
  const req = silent
    ? api.get('/alarm-dashboard/overview')                  // 轮询直接请求：浏览器会自动带 If-None-Match，内容没变就拿 304
    : cachedGet('alarm:overview', () => api.get('/alarm-dashboard/overview'))
  return req
    .then((res: any) => {
      setData(res.data)
      setStale(['stale', 'stale-error'].includes(res.headers?.['x-snapshot']))
      setError(null)
    })
    .catch(err => { if (!silent) setError(err.message || 'Failed to load') })
    .finally(() => { if (!silent) setLoading(false) })
}, [])

useEffect(() => {
  load()
  const timer = setInterval(() => {
    if (document.visibilityState === 'visible') load(true)  // 标签页在后台时不轮询
  }, 60_000)
  return () => clearInterval(timer)
}, [load])

// 页面顶部：
// {stale && <Alert type="warning" message={t('alarm.dataDelayed', { at: data?.generated_at })} />}
```

说明：
- 响应头是 `Cache-Control: no-cache` 加 `ETag`，浏览器会自动带上 `If-None-Match` 去重新验证。命中 304 时，axios 拿到的仍然是浏览器缓存里的完整内容，代码不用做任何特殊处理。
- `generated_at` 已经显示在页面和导出的副标题里，用户能看到数据对应的时间。

## 5. 一致性与故障处理

| 场景 | 行为 |
|---|---|
| 正常 | Worker 每分钟发布快照，Web 在 2 秒内感知到新版本 |
| 快照计算抛异常 | `safe()` 只记日志，采集任务仍然成功，旧快照保留 |
| Worker 挂了，或任务被停用 | 快照超过 5 分钟（实时）或 4 小时（历史）后，Web 单飞现算，并在进程内缓存 60 秒（与改造前一样）。响应带 `X-Snapshot: stale`；**前端横幅本 PR 未实现**（见 4.8 的提示），目前只能靠 `generated_at` 看数据时间 |
| 现算也失败（比如数据库抖动） | 继续返回旧快照，标记 `stale-error`；只有完全没有快照时才返回 500 |
| 首次部署，快照还没生成 | 第一个请求现算（和现在一样），之后都直接命中 |
| 多个 Worker 组同时发布 | UPSERT 加 version+1 是原子的，后写的生效 |
| 数据库切换 SQLite 或 PG | **快照链路只在 PG 上启用**（`alarm_snapshot.safe()` 按 `DB_MODE` 直接跳过）：它复用的 `_history_metrics_sql` / `_recovery_mttr` 是 PG 方言（`~`、`::bigint`，主分支既有实现）。SQLite 副本（便携包/冒烟）不发布快照，接口照旧走现算；注意 `/overview`、`/alarm-overview` 在 SQLite + 有 `history_alarm` 数据时本来就会在这两条 SQL 上报错（主分支既有问题，不是本 PR 引入，本 PR 也没有让它变好） |

**新鲜度没有变差：** 现在的 60 秒缓存意味着用户最多看到 60 秒前的结果；改造后，同步一完成，2 秒内就能看到新数据。

## 6. 上线步骤

用环境变量 `ALARM_SNAPSHOT` 分三档逐步切换（写在 `apps/my_app/backend/.env`）：

| 阶段 | 设置 | 做什么 | 时长 |
|---|---|---|---|
| 0 | — | 用 access.log 统计基线 p50/p95（第 8 节） | 半天 |
| 1 | `ALARM_SNAPSHOT=shadow`（**代码默认值**，合并后线上行为不变） | Worker 正常发布快照；接口仍返回旧逻辑结果，同时和快照比对，不一致时记 `[SNAPSHOT-SHADOW] mismatch` | 1–2 天，确认没有 mismatch |
| 2 | 在 `backend/.env` 里设 `ALARM_SNAPSHOT=on` | 接口改为读快照。**切之前必须先跑第 7 节的人工验收**：shadow 只比对两个 overview，`/realtime-drilldown`（走快照增强行）与 `/history-drilldown`（走物化表）这两条切 on 后才真正启用的路径它不覆盖 | — |
| 回滚 | `ALARM_SNAPSHOT=off` | 立即回到旧逻辑；快照表保留，不影响任何功能 | 改完重启即可 |

**部署时要做完这四步**（AGENTS.md 规定只改源码不算部署完成）：
1. 重建前端（`apps/_fe_dist`）。
2. 重启后端。
3. **重启 Worker**，这次 Worker 的代码也改了。
4. 读 live OpenAPI，确认接口签名，然后用 `curl -I` 检查响应头里有没有 `ETag` 和 `X-Snapshot: hit`。

```python
def _norm(o):
    return _strip(json.loads(json.dumps(o, ensure_ascii=False, default=str)))


def test_overview_snapshot_matches_inline():
    ad._cache.clear()
    inline = ad._compute_overview_payload()
    alarm_snapshot.after_realtime_sync()
    assert _norm(inline) == _norm(snapshot_store.peek_payload("alarm:overview"))


def test_history_drilldown_sql_matches_pandas():
    alarm_snapshot.rebuild_history_enriched()
    for metric in ["all", "dispatch_delay_eflow", "alarm_fetch_delay", "dispatch_overdue_total"]:
        old = ad._history_drilldown_pandas(metric, 5000)   # 原 pandas 实现，已保留为兜底
        new = ad._history_drilldown_sql(metric, 5000)        # 需要 alarm:history_enriched 门禁为 ok
        assert old["total"] == new["total"]
        # servertime 相同的行，pandas 和 SQL 的先后顺序可能不同，所以按集合比较
        key = lambda r: (r["tt_id"], r["site_id"], r["server_time"])
        assert sorted(map(key, old["data"])) == sorted(map(key, new["data"]))
```

## 8. 量化验证：从 nginx 日志统计耗时

`nginx.conf.template:46-49` 的日志格式已经包含 `rt=$request_time urt=$upstream_response_time`。

```python
import re, statistics, sys
from collections import defaultdict

LINE = re.compile(r'"(?:GET|POST|PUT) (?P<path>[^ ?]+)[^"]*" (?P<st>\d{3}) .* rt=(?P<rt>[\d.]+) urt=(?P<urt>[\d.]+)')
data = defaultdict(list)
for line in open(sys.argv[1], encoding="utf-8", errors="ignore"):
    m = LINE.search(line)
    if m and m["path"].startswith("/api/alarm-dashboard/"):
        data[m["path"]].append((float(m["rt"]), float(m["urt"]), m["st"]))

def p(xs, q):
    xs = sorted(xs)
    return xs[min(len(xs) - 1, int(len(xs) * q))]

for path, rows in sorted(data.items()):
    urt = [r[1] for r in rows]
    n304 = sum(1 for r in rows if r[2] == "304")
    print(f"{path:45s} n={len(rows):5d}  urt p50={p(urt, .5):.3f}s  p95={p(urt, .95):.3f}s  304={n304}")
```

改造前后各跑一次。验收标准：`/overview` 和 `/alarm-overview` 的 urt p95 低于 0.05s，历史下钻低于 0.3s，并且轮询请求里大部分返回 304。

## 9. 推广到其他看板

`battery_dashboard.py`、`packet_loss_dashboard.py` 等用的是同一种"60 秒 TTL 内存缓存"写法，都可以照搬：

1. 把计算逻辑抽成 `_compute_xxx_payload()`。
2. 在对应采集任务成功后调用 `snapshot_store.publish("xxx:overview", ...)`。
3. 路由改为 `_serve(...)`。

`_serve` 和 `snapshot_store` 是通用的，可以放进 `services/dashboard/`，各个看板共用。`services/dashboard_service.py` 已经实现了内存 LRU、磁盘快照和后台刷新，后续可以考虑和本方案合并成一套。

## 10. 风险与注意事项

- **快照表的可见性（H8）。** `_dashboard_snapshot` 和 `_history_alarm_enriched` 都以 `_` 开头，会被通用表浏览器的列表隐藏。但按审查报告里的 H8，`/api/tables/{name}/data` 目前仍然能读到它们。里面只有聚合结果和告警明细，与现在看板展示的内容相同，没有新增暴露面。H8 修复时把它们加进白名单排除即可。
- **疑似现有 bug，与本方案无关，请单独核对。** `history_alarm` 已统一为 TEXT 列，而 `HIS_SEV_MAP` 的键是整数（`{1: "Critical", ...}`）。历史下钻的严重度一栏可能显示成 `P1`，而不是 `Critical`。本方案为了保证口径一致，原样保留了这个行为。
- **快照大小。** 总览的 JSON 估计在几十到几百 KB，每分钟 UPSERT 一次，对 PG 来说可以忽略。日志里有 `compute_ms` 和 size，方便观察。
- **realtime_alarm 仍然在整表重建。** 看板改为读快照后，不再直接受影响，但其他读 `realtime_alarm` 的页面（gis、portal_qc）仍会遇到"表短暂消失"。建议另外把 `_sync_realtime_alarm` 也改成"写入 `__new` 表再在事务里 RENAME"，和 4.6 节的做法一样。
- **什么时候需要 Redis。** 后端改成多个 worker 或多台机器，需要跨进程推送（pub/sub），或者快照大到不适合放进数据库时，再考虑。到那时只需要把 `snapshot_store` 的读写换成 Redis 实现，接口和调用方都不用改。
