## 一、定位

利比里亚 NOC/SOC 可视化运维平台。仓库同时是**源码仓库**和**生产部署目录**：MSNOC1（192.168.100.20）上的 `D:\02_olbr_portal`，2026-11-18/19 切换为生产。它现在承载 80/443/7038/7090/9267/9268 端口和系统 PostgreSQL 5432。旧线 `D:\01_olbr_portal` 已退役，只作回滚目标；与 `D:\01_RPA` 已完全脱离。

## 四、运行与部署

- **角色标记**（ADR-0003）：根目录 `PRODUCTION.flag` 和 `ISOLATED_COPY.flag` 互斥。两个都在或都不在时，启停与检查脚本一律拒绝执行。
- **生产启停**：`start.bat`/`stop.bat` → `ops/deploy/portal-ctl.ps1`，通过三个自愈计划任务调用各子系统的 `start_hidden.ps1`。
- **隔离副本/冒烟**：`ops/deploy/start_all.ps1`（起 55432 便携 PG、8080/8443），在生产树上会直接 throw。
- **"部署完成"定义**：重建前端 + 重启后端 + 用 live OpenAPI 对照源码，三步都做才算。2026-11-11 出过前后端 split-brain 事故。
- **对外分发**：GitHub Release 发布 `noc-soc-platform-*.zip` 与 `noc-soc-runtime-*.zip`。
- **配置**：`apps/my_app/backend/.env`、`apps/whatsapp-kb-bot/.env`。根 `.env` 只给隔离副本用。
- **本地权威表**：`app.db` 中的 credentials / task_schedule_config / email_recipients 不会随迁移自动带过去。

## 六、优化建议（按优先级）

### P0：安全，建议立即处理

1. **仓库可见性**：这是 ZTE 内部生产仓库，里面有内网 IP、端口、主机名和运维细节，却是 PUBLIC。建议改为 Private，最好挂到组织账号下。如果需要公开分发，另建一个只放 Release 包的公开仓库。
2. **凭据轮换并清理历史**：README 承认 PG 口令、TT 桥接令牌和 JSESSIONID 都还留在 git 历史中。建议先轮换，再用 `git filter-repo` 或 BFG 清理历史并强制推送，同时让所有克隆重新拉取。只删当前代码是不够的。
3. **加密钥扫描门禁**：在 pre-commit 和 CI 中加入 gitleaks/trufflehog，并开启 GitHub Secret Scanning 和 Push Protection。
4. **app.db 中的 credentials 表**：建议改为加密存储（DPAPI 或 Windows 凭据管理器）或接入 Vault，避免明文落库，也方便迁移。
5. **TLS**：现在用自签证书，浏览器的警告已经被当成"预期"。建议签发内网 CA 证书并分发根证书，否则用户会习惯性忽略证书警告，增加中间人风险。

### P1：可靠性与部署

6. **源码树和生产运行树分离**：现在同一个目录既用来开发又在跑生产，"改了源码没重建/没重启"的 split-brain 风险正来自这里。建议生产只部署 Release 制品（版本化目录 + `current` 软链接或 junction），开发在另一棵树完成，切换和回滚都是原子操作。
7. **一键部署脚本**：把"重建前端 → 重启后端 → 对比 live OpenAPI 与源码"封装成 `portal-ctl.ps1 -Action deploy`，部署后自动做冒烟检查和版本号校验，比如前后端都暴露 `/version` 并返回 git SHA。
8. **单机单点**：nginx、后端、PG 都在 MSNOC1 一台机器上。至少应做到 PG 定时备份到异机并演练恢复（`pg_dump` + WAL 归档），可以再考虑冷备机方案。
9. **减少对本机 GUI 组件的依赖**：CN EMS Java 客户端、Chrome/Edge 自动化、FineBI 导出目录都是隐性依赖。建议把这些采集任务收进 agent-worker，用 Linux worker 加无头浏览器执行，并加上健康探针和失败告警。
10. **统一数据库**：SQLite（app.db）和 PG 并存，迁移时会漏掉权威表。建议把这三张表迁到 PG，用 Alembic 管理迁移，把 SQLite 降级为仅开发使用。

### P2：架构与可维护性

11. **去掉相对路径耦合**：ADR-0001 的约束说明子系统之间通过"父目录/兄弟目录"寻址，比较脆弱。建议改为显式配置（环境变量或配置文件给出路径），长期可改成 HTTP 接口调用，比如 bot 暴露通知 API，my_app 不再直接调用它的脚本。
12. **统一鉴权**：门户的 Node 鉴权和 my_app 各自独立。建议统一为 OIDC/SSO（例如 Keycloak，或对接公司 AD），nginx 层用 `auth_request` 统一拦截，并补齐审计日志。
13. **可观测性**：引入结构化日志加集中收集（Loki/ELK），用 Prometheus 指标和 Grafana 面板覆盖端口健康、采集任务成功率、告警延迟。作为 NOC 平台，它自己也需要被监控。
14. **容器化（可选）**：如果 Windows 主机允许，可以用 Docker Compose 封装 nginx、my_app、portal、bot，消除"系统 Python/Node 版本"的差异。即使不上容器，也建议固定运行时版本，并在 Release 中附上 SBOM。

### P3：工程流程

15. **控制 CI 自动化的风险**：auto-fix 和 auto-merge 让 AI agent 可以自动合并到 main，而 main 又直接对应生产树。建议给 main 加分支保护，至少要求一名人工 review 和必需检查通过；auto-merge 只放行低风险标签，比如 docs 类。
16. **测试**：README 提到发布包里不含测试，建议在 `quality.yml` 中明确单元/接口测试的覆盖要求，并补上前后端契约测试，用 OpenAPI 生成前端类型，从根上防止 split-brain。
17. **精简文档**：`.gitignore` 有 40 KB，`AGENTS.md` 有 42 KB，说明约束靠文字堆积。建议把关键约束尽量变成脚本断言，`check_all.ps1` 已经有这个方向；保留 ADR，把 AGENTS.md 精简为索引。
18. **依赖更新**：开启 Dependabot/Renovate，覆盖 npm、pip 和 GitHub Actions。

## 七、建议的落地顺序

| 阶段 | 时间 | 内容 |
|---|---|---|
| 第 1 周 | 立即 | 仓库转私有、凭据轮换、清理历史、开启密钥扫描、main 分支保护 |
| 第 2–4 周 | 短期 | PG 异机备份、一键 deploy + 版本校验、权威表迁入 PG |
| 1–3 个月 | 中期 | 制品化部署（源码与运行分离）、统一 SSO、可观测性 |
| 3 个月以上 | 长期 | 去除相对路径耦合、采集任务迁到 worker、可选容器化/高可用 |
