## 一、总体结论

本轮共 **8 条高危、14 条中危、若干低危**。首轮的 16 个问题在最新代码上**都没有修复**。新增问题中最严重的是：

1. **H9：不登录就能拿到上游系统的明文共享账号。** 8088 端口反代 `inject.js` 时没有带代理头，后端把请求当成本机发起，于是绕过登录，直接返回带明文用户名和口令的填表脚本。
2. **H10：本机回环被视为"免登录"。** 在 MSNOC1 上，浏览器直接访问 `127.0.0.1:7038` 时不带代理头，会被当成本机放行。CORS 又允许任意 `*.app.workbuddy.link` 子域携带凭据读取响应。结果是：只要在这台机器上用浏览器打开一个恶意页面，就可能调用全部 API，包括查看凭据明文。

这两条和首轮的 H1、H2、H5、H6、H8 一起，构成多条从"外部人员或任意登录用户"到"拿到全部上游凭据"或"在生产机上执行代码"的路径。

**做得好的地方：**
- 门户密码用 scrypt 加盐。
- 登录有按 IP 的限流和锁定（10 次失败锁 60 秒）。
- 首次登录强制改密。
- 会话 Cookie 带 HttpOnly 和 `SameSite=Lax`。
- workflow 都通过 env 中转事件字段，没有直接把 `${{ }}` 拼进脚本，避免了脚本注入。
- 门禁脚本取自 main 检出。
- 本机代理只监听 127.0.0.1。
- bot 的会话凭据和问答库都已 gitignore。
- 表名和列名做了标识符校验（`_safe_ident`）。
- 附件上传有大小限制、后缀黑名单和路径穿越防护。

**H9/H10 修复示例（security.py）：**

```python
# 内部调用必须显式出示令牌；"没有代理头"不再等于本机
API_TOKEN = os.environ.get("MY_APP_API_TOKEN", "")

def client_is_internal(request: Request) -> bool:
    peer = request.client.host if request.client else ""
    if not _is_loopback(peer):
        return False
    tok = request.headers.get("X-Internal-Token", "")
    return bool(API_TOKEN) and secrets.compare_digest(tok, API_TOKEN)
```

改完之后，调度器、看门狗、bot 这些本机调用方要统一带上 `X-Internal-Token`。在 nginx 的所有反代 location 里加一行 `proxy_set_header X-Internal-Token "";`，防止外部请求伪造这个头。

### 🟢 低危 / 改进项

- **L1：** GitHub Actions 只固定到大版本（`actions/checkout@v4` 等），没有固定到 SHA。在有 `contents: write` 权限的 workflow 里建议固定 SHA。
- **L2：** `pr-merged-writeback.yml:59-72`、`ci-failure-notify.yml:46` 把 `pull_request.body`、`head.ref`、`head_branch` 经 env 传进脚本，目前写法安全。以后修改时不能改成直接内联 `${{ }}`。
- **L3：** bot 调用 my_app 的 `/api/bot-data/*` 时不带任何凭据（`datadomains.js:55-66`），完全依赖 H9/H10 里的"本机放行"。按 H9 ② 改造后，bot 需要带上内部令牌。
- **L4：** 门户 `clientIp()`（`auth/routes.ts:55-69`）在对端是回环时信任 X-Real-IP 和 XFF。如果某个端口没有覆盖这两个头（同 H9），客户端可以伪造它们来绕过登录限流。
- **L5：** `task_runner.py` 用的是 APScheduler 加进程内锁，只适用于单进程。
- **L6：** `inject.js` 的注释承认"任何能访问 my_app 的客户端都能拿到共享账号"。这是一个被接受下来的设计风险，建议正式记录进风险登记并设定整改期限。
